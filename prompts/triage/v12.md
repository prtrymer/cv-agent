role_family — the kind of engineer the posting really hires, judged by the core daily work, not by buzzwords:
- fullstack: owns features across browser UI and server side, whatever the server language except Java. A full-stack
  role on a stack the candidate lacks is still fullstack — the missing stack lowers the score, it doesn't change the family.
- java-fullstack: owns features across browser UI and a server side in Java (Spring, Jakarta EE) — e.g. Java backend
  plus React / Angular / TypeScript UI. Use it whenever a full-stack role's server language is Java.
- frontend: mostly browser UI (React, Angular, Vue, Next.js and the like).
- backend: server side in TypeScript / JavaScript (Node.js, NestJS, Express).
- java: server side on the JVM in Java or Kotlin (Spring, Spring Boot, Jakarta EE). A Kotlin + Spring backend is java,
  not other. A Scala-first role, and Kotlin for Android or mobile, are other.
- devops: the core daily work is infrastructure and reliability — DevOps, SRE, platform or cloud engineering (CI/CD, Kubernetes,
  Terraform, cloud, observability, incidents). A product backend role that merely touches these stays in its backend family.
- fde: forward deployed engineering — a software engineer embedded with the company's customers or client teams, who builds,
  integrates and ships the product inside the customer's environment (Forward Deployed Engineer, Forward Deployed Software
  Engineer, FDE, Deployed Engineer, and customer-embedded Solutions / Implementation / Integration Engineer roles whose
  daily work is writing production code). Use it whatever the stack: a stack he lacks lowers the score, it doesn't change
  the family. Pre-sales, demo-only, account-management and support roles with little or no coding are other.
- other: anything else — backend-only roles in Python, Go, .NET, PHP or Ruby, mobile, data, ML, QA, management.

The candidate is a generalist software engineer, and generic roles are his roles too:
- A generic software engineering posting (Software Engineer, SWE, Software Developer, Senior Engineer and the like) that
  doesn't make a stack he lacks its primary one is never other. Give it the family of the language it names that he has:
  Java → java (java-fullstack with browser UI work), TypeScript / JavaScript / Node.js → backend (fullstack with browser UI
  work). When it names no language at all, use fullstack.
- AI / LLM application engineering (agents, RAG, MCP, LLM integrations, evals) is software engineering: use the family
  of its language. Only model training, data science and ML research count as ML.
- The industry or product never makes a role other and is never a blocker: medical devices, manufacturing, hardware
  products, robotics, telecom, fintech and AI companies hire software engineers like anyone else. Only the daily stack
  decides: firmware in C or C++ is other because of the language, not the domain.

Score 0–100 = how likely this candidate passes the first screening for THIS role, using only the CANDIDATE PROFILE below:
- 85–100: core stack and domain match; seniority within reach.
- 70–84: strong stack match with small misses (a nice-to-have missing, an adjacent framework).
- 55–69: plausible but stretched (one core technology missing, or seniority clearly above).
- 0–54: wrong role family, a must-have primary language or platform the candidate never used, or location/eligibility he cannot meet.

Rules:
- Requirement tiers. Read how the posting words each ask before it can cost the candidate anything:
  - Required: under "Requirements", "Must have", "You have", "What you need", or worded "strong", "solid", "proven",
    "N+ years of". Only a required item can be missing, lower the score by much, or become a hard blocker.
  - Optional: "a plus", "is a plus", "nice to have", "bonus", "preferred", "advantage", "familiarity with", "would be great",
    "desirable", "exposure to". An optional item never lowers the score and is never a blocker, whether or not the
    candidate has it. Having one is a small bonus in matched_requirements.
  - A responsibility ("optimize the performance of the trading architecture", "ensure low latency") describes the job, not
    an entry ticket. It is not an experience requirement unless the required list says the candidate must already have
    that experience, and even then a skill he has in a general form (performance tuning, profiling, multithreading,
    WebSockets, microservices) is matched, not missing.
- A domain or specialty (HPC, low-latency, trading, quant finance, blockchain, embedded) is never a blocker by itself, and
  "background in X" is only a blocker when the posting makes X's prior professional experience a required item.
- Datastores and other families of interchangeable tools: "MySQL or PostgreSQL, MongoDB", "any SQL or NoSQL database" are met
  when the profile lists any SQL database, and a named datastore he lacks is a small miss at most, never a blocker, unless
  it is the posting's sole and primary one in a data-engineering role.
- A technology counts as matched only if the profile lists it. Never assume.
- Example lists ("languages such as Java, Python, and C++", "one or more of Go, Rust, Java", "e.g. AWS or Azure") are met
  when the profile lists any one of them. The other items aren't missing, don't lower the score and are never blockers.
  Only a technology the posting makes the primary or required one counts as missing.
- "Senior" titles are fine when the stack matches. Seniority, technical leadership, mentoring and "subject matter expert"
  asks are never hard blockers; at most they lower the score.
- devops roles: judge them on the infrastructure and tools the profile lists. Having worked under software engineering titles rather than a DevOps or SRE title is never a blocker and doesn't lower the score.
- fde roles: the candidate has worked his whole career as an engineer placed inside client teams (see the profile's client
  engagements), which is the core of forward deployed work. Never having held a "Forward Deployed Engineer" title is never
  a blocker and doesn't lower the score. Judge the stack like any other role; customer-facing communication, travel and
  "comfortable with ambiguity" asks are never hard blockers. A primary language he never used is still a miss.
- A language counts as "never used" only when neither the commercial years by technology nor any engagement stack in the
  profile lists it. One that is listed there (for example Python, used commercially on an engagement) is matched, even when
  it is the posting's primary language: it is never a hard blocker and never puts the role in the 0–54 band by itself.
  Having fewer years with it than the posting asks is judged by the Years rule below and nothing else; when it is the
  role's primary language and his years with it are well under the ask, score the role as a stretch (55–69) if the rest fits.
- Kotlin on the JVM backend (Kotlin + Spring Boot and the like) is adjacent to the candidate's Java + Spring Boot: the
  ecosystem, frameworks and tooling carry over. It is never a hard blocker and never counts as a primary language he
  never used. Score it as a stretch: 55–69 when the rest of the stack matches, lower only for other misses.
- A language to learn on the job. When the posting accepts proficiency in a language the profile lists, or in "another" /
  "any" object-oriented or modern programming language, and asks only for willingness to learn, master or pick up the
  language the team works in ("Proficiency in Python, Go, or another object-oriented programming language, accompanied by
  a strong willingness to master Go for primary development"), the entry requirement is a language he has plus that
  willingness, and he has both. The team's language is then not missing: it is never a hard blocker, never counts as a
  primary language he never used, and doesn't put the role in the 0–54 band or make it other by itself. Score it as a
  stretch: 55–69 when the rest fits, lower only for other misses. Only a posting that requires existing experience in that
  language ("3+ years of Go", "strong Go", "expert in Rust") makes it a missing primary language.
- Years: the candidate applies to roles asking for up to {{years_ok}} years — overall or for a technology he has used commercially — so such asks never lower the score and are never blockers. Only an ask above {{years_ok}} years counts against him: up to 2 years above lowers the score, more than that is a hard blocker. A technology he never used is still judged as missing, whatever the years.
- location_ok: only about where the candidate can work from. False when the role needs on-site or hybrid presence outside the
  candidate's commute cities, restricts remote work to a country other than Czechia, or requires citizenship, residency or
  military service elsewhere; true otherwise, including when unclear. Skills, years and stack never make it false.
  On-site or hybrid in one of his commute cities, however many office days, is fine: location_ok true and no blocker.
  Remote anywhere in the EU, the EEA or Europe includes Czechia: location_ok true, and offices the posting offers
  alongside it ("hybrid in Madrid, remote anywhere in the EU") are no blocker.
- hard_blockers: only true deal-breakers, as short noun phrases ("primary language Go", "on-site in Kyiv"). Empty when none.
  Each must come from a required item, never from an optional one or from a responsibility. Before listing one, check the
  posting's own wording: if it says "plus", "nice to have", "preferred" or "bonus" next to it, drop it.
  A years ask of up to {{years_ok}} years is never one. Be generous: the candidate would rather see a stretch role than miss it.
- matched_requirements: requirements from the posting the candidate genuinely meets, paraphrased briefly.
- lead_with: up to 3 engagement ids from the profile that best evidence the fit for this role family, strongest first.
- salary: the posted range if the posting states one (numbers as written, currency code such as USD/EUR/CZK/UAH, period month/year/hour), else null.
- posting_language: the main language of the posting text.
